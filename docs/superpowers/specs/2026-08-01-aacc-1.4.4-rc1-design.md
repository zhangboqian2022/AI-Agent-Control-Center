# AACC 1.4.4-rc1 整改与候选版设计

**日期：** 2026-08-01
**基线：** `main` 合并提交 `2f93f8840422f03c49ecfd7f4b81a448bf3e0ecc`（AACC 1.4.3）

## 目标

基于四组历史评审材料和合并后 main 的 CI 证据，修复当前可复现的状态误报、安全边界和发布门禁问题，产出可审计的 `1.4.4-rc1` 候选版。评审意见只作为待核验假设，不直接视为事实；每个接收项必须有回归测试或明确的证据边界。

## 评审裁决

### 本次接受并纳入 rc1

1. main CI 的发布文档测试仍检查旧截图路径；测试契约必须与已合并的 1.4.3 版本化截图同步。
2. OpenCode 新鲜 `tool/pending` 应立即显示 `WAITING_APPROVAL`，不应先显示蓝色运行；明确的 `error/failed/rejected/cancelled` 应映射为错误或取消。
3. OpenCode 仅因进程消失不得伪造绿色完成；只有明确的 `step-finish`/完成证据才能进入 `COMPLETED`，否则显示 `STOPPED` 或 `UNKNOWN`。
4. Kimi `turn.cancel` 是取消，不是成功完成。
5. 终态后的活动候选必须通过更新时间和新一轮证据检查，不能让旧的低可信度事件把绿色状态重新改蓝。
6. 动态任务已存在时不应每轮重复执行完整 SQLite 初始化。
7. 修复 loopback CLI/wrapper 的环境代理继承，修复 `doctor` 忽略 `PRAGMA quick_check` 返回值的问题。
8. 加固 OpenCode workspace URL、Daimon 候选路径日志和 AppleScript `\r` 转义。
9. 为评审透明度提供双语整改矩阵、测试映射和真实证据边界；不把 Windows Server CI 宣称为消费级 Windows 10/11 真机验证。

### 部分接受，保留为后续或条件风险

1. 配置写入 TOCTOU：当前已有拒绝符号链接、同目录临时文件、权限保护和原子替换；本候选版先补充替换前目录句柄/安全检查及回归测试，完整的跨平台目录句柄方案另列后续安全迭代，不能声称已经消除所有本地攻击者竞态。
2. Windows 文件锁：现有失败路径会关闭句柄，风险低；rc1 增加竞争回归与诊断，不在没有 Windows 原生 Mutex 测试环境时贸然替换锁协议。
3. 终端注入：已有单线程有界执行器和完整操作锁，但窗口选择仍需 fail-closed。rc1 要求非空稳定目标、唯一匹配和注入前焦点复核；完整跨平台 `TargetLease`/PID 绑定需要真实窗口自动化证据后再扩展。
4. aacc-run 子进程树：当前直接进程生命周期语义真实且不会伪造完成；补齐 Unix 进程组和 Windows Job Object 属于后续平台专项，文档不得夸大为已清理全部后代。
5. Adapter：评审指出 Adapter 定义没有运行时消费者，这一部分部分成立。为兑现“可配置 Adapter”而不扩大语义，本次接入独立的进程级 Adapter 发现服务；非原生任务只报告运行/停止，完成、审批和输出仍必须通过 API/CLI/`aacc-run` 等结构化来源上报。
6. 未签名、未公证和消费级 Windows 10/11：这是分发和人工验收限制，不由代码测试伪造解决。rc1 保留明确限制、校验步骤和 CI 资产证据。

### 不接受的历史判断

1. 旧评审中“送审副本没有 `uv.lock`”不能用于否定当前 GitHub 源码：当前仓库已跟踪 `uv.lock`，CI 使用 `uv sync --locked` 并成功执行过完整流水线。若导出送审副本，必须把锁文件、测试、工作流和报告作为可复核材料明确列出。
2. 早期关于配置 Token 为空、普通写入 0644、GUI 同步执行自动化、历史记录无限增长、OAuth 无代际保护等结论，按当前源码已落地的修复和现有测试重新判定，不在 rc1 重复实现。

## 架构与数据流

状态链路保持：外部本地证据 → 发现/解析器 → `TaskState` → `StateMachine` → `TaskManager`/SQLite → GUI。状态解析只能使用明确事件或有界时间证据；进程消失本身是“停止/未知”证据，不是业务成功证据。

自动化链路保持：GUI/API/热键 → 有界单消费者 `AutomationExecutor` → 平台控制器。注入操作在同一事务中完成目标解析、聚焦、延迟、焦点复核和输入；目标不唯一、为空或复核失败即拒绝。

发布链路保持：源码和锁文件 → macOS/Windows CI → coverage/diff-cover/pip-audit/打包 → rc1 资产与 SHA-256 → 双语发布说明和限制。未完成真机门禁的项目只能作为候选版并准确标注。

## 交付分层

### 阶段 A：修复 main 合并后的 CI 阻塞

更新 `tests/test_release_docs.py` 对版本化截图路径和新说明文字的断言，先在本地重现失败、修复、再推送 main，等待 macOS、Windows 2022、Windows 2025 全套 CI 通过。

### 阶段 B：实现 rc1 真实修复

以失败测试开始，依次处理 OpenCode/Kimi 状态真值表、状态机乱序、SQLite 注册路径、loopback 客户端、doctor、URL/日志/AppleScript 和窗口注入边界。每一组修改独立测试，禁止把评审中未证实的大重构混入同一提交。

### 阶段 C：版本与评审材料

按项目约定同步 `__version__`、`pyproject.toml`、`uv.lock`、双语 CHANGELOG 和 `docs/release-notes-1.4.4rc1.*`；提供整改矩阵、测试函数映射、CI 链接和未完成人工门禁清单。候选版通过 CI 后再决定是否合并回 main；远程分支在确认 main 含最终提交后清理。
