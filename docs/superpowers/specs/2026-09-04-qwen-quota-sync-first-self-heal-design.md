# Qwen 百炼额度：同步优先登录与受保护自愈设计

日期：2026-09-04
分支：待建（建议 `fix/qwen-quota-sync-first-selfheal`，自 main）
状态：设计已获用户确认，待实施
前序设计：`2026-08-05-qwen-headed-hidden-refresh-design.md`（有头隐藏刷新）

## 1. 背景与证据

AACC 的 Qwen（阿里云百炼 token-plan）额度由 AACC 自管的隔离 Chrome（CDP
驱动）抓取：可见窗口登录一次，之后每 15 分钟一次「有头但隐藏」的刷新；
`qwen_auto_session_recopy: true` 时，刷新撞见登录横幅会把日常 Chrome 的
最小会话集复制进受管 profile 并重试。

2026-09-04 上午真机日志实锤了用户报告的「缓存很快就掉了」：

| 时间 | 事件 |
|---|---|
| 11:44:10 | 启动刷新 → 判过期 → 重复制（日常会话已死）→ 未登录 |
| 11:45:32 | 用户可见登录 → **11:46 成功**（状态写回 `reuse=true`） |
| 11:55:38 | 定时刷新在**登录成功 9 分钟后**判「未登录」→ 自动重复制用死掉的日常 cookie **覆盖了 9 分钟前刚登录的新缓存** → 重试仍失败 → 又要求登录 |
| 12:05 | 用户在日常 Chrome 里登录百炼 |
| 12:14:18 | 刷新重复制（日常会话已活）→ **12:14:24 成功** |
| 12:29:14 | 12:14 同步来的会话**已死（存活 <15 分钟）** → 再次重复制 → 12:29:20 成功 |
| 12:44 | 同形态再来一轮，成功 |

补充观察：

- 11:46 登录成功后，登录用的 Chrome 进程 6 分钟后仍存活（正常应在 ~5 秒内
  退出）——滞留进程是 Dock 图标带运行小圆点「残留」的直接来源。
- 12:07:33 的登录尝试在 14 秒后被代码自动判为「用户关窗」并关闭——现有
  「3×2s 没看到百炼页面 = 用户取消」的判定会把跨域跳转（短信验证码页在
  别的域名）误判为关窗。
- 8 月基线（2026-08-06）：同样的日常会话复制在隐藏刷新里存活 **5.5 小时、
  20+ 轮**；8/29 构建之后每一轮隐藏刷新都被判未登录，8/31 起重复制+重试
  连续失败（期间日常 Chrome 一直没登录百炼）。

推导结论：

1. **隐藏受管 Chrome 呈现的会话现在几分钟内即被风控作废，与登录地点无关**
   （手动登录的活 9 分钟，日常复制来的活 <15 分钟）。8 月能活 5.5 小时，
   说明存在能活的配置；变量候选：Chrome 150/151→152、阿里风控收紧、
   「日常 Chrome 与隐藏 Chrome 并发出示同一票据」触发风控。
2. **只要日常 Chrome 的百炼会话活着，「每轮重复制」是可靠的稳态供数路径**
   （12:14/12:29/12:44 三轮连续成功，复制幂等）。
3. 「首次撞横幅即重复制」在手动登录场景会摧毁刚建好的健康缓存——这是
   用户感知「越修越坏」的直接原因。
4. 登录体验三缺陷：窗口不居中、成功后进程滞留、14 秒误取消。

## 2. 已批准的需求决策（用户 2026-09-04 确认）

| 决策点 | 结论 |
|---|---|
| 登录主路径 | **同步优先**：点击授权先静默同步日常 Chrome 会话并隐藏取数，成功即显示额度（「点击自动就同步」）；失败才弹登录窗 |
| 失效后行为 | **自动弹出**居中登录窗，用户输手机验证码，登录后自动恢复；弹窗限频 |
| 登录窗位置 | 屏幕正中（当前为 Chrome 默认位置，缺陷） |
| 进程卫生 | 操作用完必须彻底退出全部受管 Chrome，不留滞留进程（Dock 运行态小圆点残留的根因） |
| 不承诺项 | 阿里云服务端会话过期是服务端行为，本设计只保证快速自愈与诚实提示，不承诺「登录一次永不过期」 |
| 范围外 | Windows Edge 路径、Kimi/OpenCode 会话、任务发现服务 |

## 3. 设计

### 3.1 同步优先的登录流程

`open_login`（用户点击与自动弹窗共用同一入口）改为顺序尝试：

1. **静默同步**：若 `daily_chrome_session_source()` 存在——清理受管 profile
   滞留进程 → `recopy_qwen_daily_chrome_session` → 复用现有隐藏取数机制
   跑一次（无窗口，约 10~30 秒）。成功 → `quota_received`，流程结束。
2. **失败兜底**：无同步源或同步后取数失败 → 现有可见登录流程（窗口居中，
   见 3.4）。
3. 无论哪条路径成功，都按 3.2 记录会话来源与成功时间。

UI 文案（中英双语）：同步中显示「正在同步日常 Chrome 会话…」；转入弹窗
显示「同步失败，正在打开登录窗…」。

### 3.2 会话来源标记与受保护自愈

状态存储（`qwen-web-session-state.json`，版本号升到 2）新增字段：

- `session_origin`: `"daily_recopy" | "manual_login"`——最近一次成功会话的来源；
- `last_success_epoch`: 最近一次成功的本地时间戳。

旧文件（v1）迁移时 `session_origin` 缺省按 `manual_login` 处理（保守：宁可
多验证一轮，不可误覆盖）。

刷新撞见登录横幅（`QwenChromeUnauthorizedError`）时按来源分支：

- **来源 = 同步**：立即重复制 + 重试（12:14/12:29/12:44 验证有效的稳态；
  复制幂等，不存在摧毁问题）。重复制本身失败（源缺失/文件不全）→ 转弹窗
  路径（受限频约束）。
- **来源 = 手动登录**：**先不覆盖**，60 秒后同一操作内复检一次（防页面
  瞬时误报——11:55 事故正是「9 分钟前的新登录被一次横幅判定摧毁」）。
  复检仍是横幅 → 会话确死，覆盖已无损 → 先试同步+重试；同步不可用或仍
  失败 → 弹窗路径。
- 手动登录会话在复检后恢复（第二次判定为配额）→ 只更新时间戳，不动缓存。

**自动弹窗**：会话确认死亡且同步救不回时，会话层发信号，GUI 自动调用
`open_login`（即 3.1 全流程）。限频：30 分钟内最多自动弹一次（进程内存
量即可，重启重置可接受）；每次自动弹窗记 WARNING。**用户主动登出
（`logged_out_by_user=true`）永不触发自动恢复**，与现状一致。

### 3.3 根因探针实验（T1–T4）

目的：找出「隐藏呈现的会话为何从 5.5 小时掉到 <15 分钟」。全部为真机
实验，跑前退出 AACC（或暂停其定时器）避免 profile 竞争，跑完清理受管
profile 全部进程。

| 实验 | 内容 | 检验假设 |
|---|---|---|
| T1 | 清空受管 profile → 可见登录（登录页也装 3.4 的反检测脚本）→ 每 5 分钟隐藏取数测存活 | 「CDP 附着/`navigator.webdriver` 暴露在登录窗口期污染手动登录的会话」 |
| T2 | 同步后请用户**退出日常 Chrome** → 同样间隔测存活 | 「日常与隐藏实例并发出示同一票据触发风控」 |
| T3 | 对照：同步后日常 Chrome 保持打开（复现今日 <15 分钟） | 基线 |
| T4 | 若 T1–T3 均 <15 分钟：A/B 启动方式（8 月的直接 exec + `--no-startup-window` vs 现行 NSWorkspace 隐藏实例）与「常驻单实例」（登录 Chrome 不退出、窗口推出屏外、每轮直接复评同一标签页） | 启动指纹 / 实例生命周期 |

判定标准：存活 ≥2 小时视为「找到可活配置」（8 月基线 5.5 小时）；按证据
选修法并入主代码。若全部 <15 分钟：接受 3.6 的降级稳态，不再追逐隐藏刷新
的长存活。

### 3.4 登录窗居中与健壮取消

**居中**：CDP 端点就绪且首个页面目标出现后，`Browser.getWindowForTarget`
→ `Browser.setWindowBounds` 把窗口放到主屏可用区正中，尺寸 1100×700（与
隐藏刷新一致，百炼小窗会触发「移动端体验」拦截页，不得更小）。屏幕几何
由 Qt 侧（`QGuiApplication.primaryScreen().availableGeometry()`）算好注入，
保持 CDP 模块平台无关、可单测。

**反检测脚本补装**：现有 `install_qwen_hidden_page_stealth`（掩盖
`navigator.webdriver`、伪装负坐标）只在隐藏路径安装；可见登录路径同样
安装（T1 的前提，也独立降低手动登录会话被污染的概率）。

**健壮取消**：废弃「3×2s 没看到百炼页面 = 用户关窗」。新规则：

- 曾出现过至少一个页面目标后，连续 3 次轮询（2s/次）**一个页面目标都没
  有**（任意域名）→ 判定用户关窗，干净关闭；
- 或端点就绪 30 秒内始终零页面目标 → 判定启动异常，同样按取消处理；
- 页面跳去非百炼域（短信验证、风控验证）**不再是取消信号**——只要还有
  页面目标就继续等，登录截止时间（15 分钟）仍兜底。

### 3.5 用完必退（进程与 Dock 卫生）

- 诊断并修复滞留：在 `_shutdown_process` 打点记录走了哪条退出路径；
  `Browser.close` 前后核对主进程 PID（怀疑 Chrome 换进程 re-exec，导致
  「子进程已退出」的判定失效）。
- 每次操作结束增加硬校验：按受管 profile 轮询进程列表直至为空
  （预算 `EDGE_SHUTDOWN_TIMEOUT_SECONDS`），超时逐级 terminate→kill，
  最终仍非空记 ERROR（现状静默）。
- 保留现有三道清理：启动前清理、登出/关闭时清理、未登录路径的一次性孤儿
  清理。
- 探针期间在 Chrome 152 上复核隐藏实例不产生 Dock 磁贴。
- 边界说明：用户把 Chrome 固定在程序坞，图标本身常驻属用户设置；AACC 的
  承诺是**受管 Chrome 零滞留进程**（不给图标挂运行态）。

### 3.6 错误展示与降级稳态

额度条状态文案（中英双语）：同步中 / 登录窗已打开 / 会话已过期（正在自动
恢复）/ 点击授权。每次进入未登录态记 WARNING（rc.3 已有），不再有静默
掉线。

若 3.3 探针未找到长存活配置，产品稳态即为今日已验证的行为：**日常 Chrome
登录着百炼 → 每 15 分钟自动同步取数，额度常新；日常会话死了 → 自动弹窗
让用户登一次（该会话本身也活不长，文案如实说明）**。

## 5. 风险

1. 阿里风控可能已针对整类隐藏呈现——探针全败时只能落到 3.6 降级稳态
   （今日可用，但手动登录会话同样短命，文案需诚实）。
2. T1/T2 需要用户配合（清空 profile 后重新登录、临时退出日常 Chrome）。
3. 「操作内 60 秒复检」让手动来源从「确认死亡」到「开始自救」多花 60 秒，
   换取不误覆盖健康缓存——这是 11:55 事故的直接对价，值得。

## 6. 验收标准

1. 日常 Chrome 已登录百炼时点击授权：不弹登录窗，60 秒内显示额度
   （冷启动取数最坏可到 ~70 秒，此处按宽松口径验收）。
2. 日常未登录时点击授权：登录窗居中；手机验证码登录后显示额度；成功后
   10 秒内受管 Chrome 全部退出，零残留进程。
3. `session_origin=manual_login` 且撞横幅：不发生立即重复制（单测钉死）。
4. `session_origin=daily_recopy` 且撞横幅：立即重复制+重试（保留今日稳态）。
5. 会话确认死亡且同步不可用：30 分钟内最多自动弹一次居中登录窗；用户主动
   登出后永不自动弹。
6. 登录页跳转到非百炼域（短信/风控验证）不再触发 14 秒自动取消。
7. `ruff check`、`ruff format --check`、`mypy`、全量 `pytest` 绿；diff-cover
   改动行覆盖率 ≥90%。
